# Общий архитектурный план и видение проекта Voxellaneous

## 1. Концепция (Vision)
Цель проекта — создание воксельной экосистемы (а-ля Roblox/Teardown), где:
1.  **Основа**: Высокопроизводительный воксельный движок на WebGPU (браузер + десктоп).
2.  **Экосистема**: Пользователи создают "Плейсы" (Places), которые включают карту (воксели), скрипты и ассеты.
3.  **Мультиплеер**: Авторитетные серверы (Authoritative Server) для предотвращения читерства, с поддержкой как официального хостинга, так и self-hosted решений.
4.  **Моддинг**: Глубокая система плагинов, позволяющая менять логику игры безопасным способом.

## 2. Текущее состояние (As-Is)
*   **Рендер**: WebGPU, переписан на TypeScript. Умеет грузить `vox` модели, но сцена статична.
*   **Логика**: Hardcoded в `main.ts`. Нет разделения на движок и игру.
*   **Сеть**: P2P Mesh через WebRTC. Каждый клиент доверяет всем остальным. Сервер только сигнализирует (handshake).
*   **Физика/Игровой процесс**: Отсутствует (только полет камеры).

## 3. Целевая архитектура (To-Be)

### 3.1. Клиент-Серверная модель (Authoritative Server)
P2P Mesh не подходит для масштабных игр с защитой от читеров и сложной логикой (нагрузка O(N^2)). Переходим на модель "Звезда" (Client-Server).

*   **Сервер (Node.js / Rust / C++ Plugin Host)**:
    *   Хранит истинное состояние мира (World State).
    *   Выполняет симуляцию физики и игровую логику.
    *   Рассылает обновления клиентам (Snapshot Interpolation / Delta Compression).
*   **Клиент (TypeScript/WebGPU)**:
    *   "Тонкий" клиент. Принимает инпуты от игрока, отправляет их серверу.
    *   Предсказывает движение (Client-Side Prediction) для отзывчивости.
    *   Интерполирует состояние других объектов для плавности (Reconciliation).

### 3.2. Игровой движок (Engine Core)
Необходимо выделить ядро (Engine), отделив его от контента.

*   **ECS (Entity Component System)**: Идеально для воксельных миров.
    *   `Entity`: ID объекта.
    *   `Component`: Данные (Position, Velocity, VoxelModel, Script, Collider).
    *   `System`: Логика (PhysicsSystem, ScriptSystem, NetworkSystem).
*   **Мир (World)**: Контейнер для всех энтити и чанков вокселей.

### 3.3. Плагинная архитектура (Plugin System)
Для безопасности и производительности пользовательских скриптов предлагается использовать **WebAssembly (Wasm)**.

*   **Изоляция**: Скрипты пользователей компилируются в Wasm и исполняются в песочнице (sandbox).
*   **API**: Движок предоставляет API (Host Functions) для скриптов: `moveObject()`, `spawnEntity()`, `raycast()`.
*   **Языки**: Пользователи могут писать на AssemblyScript (TypeScript-like), Rust, Lua (через Wasm-интерпретатор).

### 3.4. Сетевой протокол
WebRTC DataChannels хороши, но для authoritative сервера можно рассмотреть **WebTransport** (современная замена WebSocket на базе QUIC/HTTP3) для низкой задержки и надежности (unreliable/reliable streams).

*   **Транспорт**: WebTransport (с фоллбэком на WebSocket).
*   **Протокол**: Бинарная сериализация (BitBuffer, Schema-based как Protobuf или кастомный).

## 4. План перехода (Roadmap)

### Этап 1: Фундамент (The Core Refactor)
1.  [Refactor] Выделить `GameWorld` и ECS из `main.ts`.
2.  [Feature] Реализовать базовую физику (AABB Collisions) на клиенте.
3.  [Arch] Разделить код на `common` (общая логика) и `client`/`server`.

### Этап 2: Авторитетный сервер (Networking)
1.  [Net] Переписать `NetworkClient` для работы с одним сервером (не Mesh).
2.  [Server] Перенести логику движения на сервер (простая валидация координат).
3.  [Feature] Client-Side Prediction для локального игрока.

### Этап 3: Моддинг и Скриптинг
1.  [Scripting] Интегрировать Wasm-рантайм (например, Extism или базовый WebAssembly API).
2.  [API] Создать базовый API движка для скриптов.
3.  [UI] Редактор свойств объектов на клиенте.

### Этап 4: Экосистема
1.  [Platform] Система аккаунтов и список серверов.
2.  [Storage] Хранение "Плейсов" в базе данных/S3.
3.  [Launcher] Возможность запускать выделенный сервер одной командой.
