# Анализ мультиплеера и сетевой архитектуры

## 1. Текущая реализация (As-Is)
На данный момент `voxellaneous` использует **P2P Mesh (Peer-to-Peer)** архитектуру через WebRTC.

### Компоненты
*   **Signaling Server (`voxellaneous-server`)**:
    *   Простая WebSocket «труба».
    *   Задача: помочь клиентам найти друг друга и обменяться SDP/ICE кандидатами.
    *   **Не знает** ничего об игре. Не видит координаты, не может проверить валидность действий.
*   **Client (`voxellaneous-web/src/network.ts`)**:
    *   Каждый клиент соединяется с каждым (`O(N^2)` соединений).
    *   Координаты (`position`, `direction`) отправляются напрямую соседям.
    *   Клиент полностью доверяет данным, пришедшим от других пиров.

### Проблемы текущего подхода
1.  **Safety / Cheating**: Любой клиент может отправить "Я нахожусь в точке X,Y,Z", и все остальные поверят. Чит на полет или телепортацию реализуется элементарно изменением пакета.
2.  **Scalability**: При росте N игроков количество соединений растет квадратично. При 10 игроках это 45 соединений. Это перегружает сеть и браузер.
3.  **Synchronization**: Нет единого "времени" или авторитетного состояния. Возможны рассинхроны (один игрок видит другого там, где его уже нет).

## 2. Требования к новой архитектуре
Для реализации "Roblox-подобной" экосистемы необходим **Authoritative Server**.

1.  **Единая истина**: Сервер хранит состояние мира. Клиенты лишь присылают намерения ("Я нажал кнопку W").
2.  **Валидация**: Сервер проверяет, может ли игрок пройти туда (коллизии, скорость).
3.  **Эффективность**: Топология "Звезда". Клиент держит всего 1 соединение (с сервером).

## 3. План миграции

### Шаг 1: Star Topology (Host-Client)
Вместо соединения всех со всеми, сделать одного из игроков (или выделенный процесс) Хостом.
*   **Dedicated Server**: Node.js (или Rust) процесс, который запускает headless-версию движка.
*   **Протокол**:
    *   **UDP / WebTransport**: Для позиций игроков (Unreliable, Ordered).
    *   **TCP / WebSocket / Reliable Stream**: Для чата, загрузки новых чанков, спавна важных объектов.

### Шаг 2: Game State Replication
Вместо отправки `Position`, сервер должен отправлять `Snapshot` мира или `Delta` изменений.
*   **Snapshot Interpolation**: Сервер шлет состояние мира 20 раз в секунду. Клиент отрисовывает игроков с задержкой в ~100мс, интерполируя между двумя последними снимками. Это дает плавность даже при потерях пакетов.

### Шаг 3: Client-Side Prediction
Чтобы игрок не чувствовал задержку на своих действиях:
1.  Клиент нажимает W -> Движок клиента *мгновенно* двигает игрока локально.
2.  Клиент отправляет инпут на сервер.
3.  Сервер симулирует и возвращает "валидную" позицию.
4.  Если локальная позиция разошлась с серверной (Server Reconciliation), клиент плавно корректируется.

## 4. Технический стек для новой сети
*   **Transport**: [WebTransport](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API) (современный стандарт) или **geckos.io** (обертка над WebRTC DataChannels для работы в режиме client-server).
*   **Serialization**: Schema-based бинарный формат. Например:
    *   [BufferSchema](https://github.com/geckosio/typed-binary-json)
    *   Protobuf
    *   FlatBuffers (нулевое копирование, очень быстро).

## Вывод
Текущую реализацию `network.ts` придется переписать практически полностью. Логика WebRTC Mesh должна быть заменена на клиент к выделенному серверу. Серверная часть (`voxellaneous-server`) из простого реле превратится в полноценное игровое приложение.
